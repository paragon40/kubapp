# Codebase

The `codebase/` directory contains the internal analysis and validation layer of SysMonitor.

Its purpose is to examine the KubApp codebase itself and produce evidence about its current structure, state, quality, security, and architectural consistency.

Unlike external infrastructure monitoring, this layer is concerned with **what is happening inside the repository**.

## Responsibilities

The codebase layer handles:

* Repository discovery.
* File and project structure inventory.
* Filesystem drift detection.
* Architecture checks.
* Security checks.
* Validation checks.
* Codebase metrics.
* Evidence generation.
* Exposing generated metrics to Prometheus.
* Providing a health endpoint for the codebase monitoring service.
* Shared execution and JSON-handling utilities.

## Main Components

| Directory/File | Purpose                                                             |
| -------------- | ------------------------------------------------------------------- |
| `docs/`        | Documentation specific to the codebase analysis layer.              |
| `evidence/`    | Generated results produced by the analysis engines.                 |
| `lib/`         | Shared shell libraries used by the runners.                         |
| `runners/`     | Analysis engines and the HTTP interface for exposing their results. |
| `README.md`    | High-level documentation for the codebase layer.                    |

## Analysis Engines

The `runners/` directory contains separate engines for different aspects of the codebase:

| Runner            | Responsibility                                                  |
| ----------------- | --------------------------------------------------------------- |
| `discovery.sh`    | Discovers and inventories the repository structure.             |
| `drift.sh`        | Checks the current filesystem against the discovered inventory. |
| `architecture.sh` | Evaluates architectural and structural rules.                   |
| `security.sh`     | Performs codebase security checks.                              |
| `validation.sh`   | Performs codebase validation checks.                            |
| `metrics.sh`      | Generates Prometheus-compatible codebase metrics.               |
| `runner.sh`       | Coordinates execution of the codebase analysis layer.           |

The runners share common functionality through `lib/` and write their results into `evidence/`.

## Codebase Metrics Service

The `runners/src/` directory contains the small Flask application used to expose the metrics generated by the analysis engines.

`src/app.py` provides three main HTTP endpoints:

| Endpoint   | Purpose                                                                |
| ---------- | ---------------------------------------------------------------------- |
| `/`        | Simple status/dashboard page for the codebase monitoring service.      |
| `/health`  | Health check confirming that the service is running.                   |
| `/metrics` | Reads and exposes `metrics.prom` in Prometheus-compatible text format. |

The application reads the metrics file from the `METRICS_FILE` environment variable.

If `METRICS_FILE` is not provided, it defaults to:

```text
/evidence/metrics.prom
```

This creates the connection between the codebase analysis engines and the observability layer:

```text
Codebase
   │
   ▼
Analysis Runners
   │
   ▼
evidence/metrics.prom
   │
   ▼
Flask metrics service
   │
   ▼
/metrics
   │
   ▼
Prometheus
```

The Flask service does not perform the codebase analysis itself. Its responsibility is to **serve the metrics already generated by the analysis layer**.

## Runner Container

The `runners/` directory also contains:

* `Dockerfile` — defines the container environment for the runner/service.
* `requirements.txt` — defines the Python dependencies required by the Flask application.
* `src/app.py` — provides the HTTP and Prometheus metrics interface.

This allows the codebase analysis and its metrics endpoint to run as a containerized component of the SysMonitor stack.

## Evidence

The `evidence/` directory contains generated output rather than source logic.

The evidence currently includes:

* `inventory.json` — discovered repository state.
* `drift.json` — filesystem/inventory drift results.
* `architecture.json` — architecture findings.
* `security.json` — security findings.
* `validation.json` — validation results.
* `metrics.prom` — Prometheus-compatible metrics generated from the analysis results.

These files allow the analysis results to be consumed by the metrics service and the wider observability stack.

## Execution Model

At a high level, the codebase analysis flow is:

```text
Repository
    │
    ▼
Discovery
    │
    ▼
inventory.json
    │
    ├──► Drift
    ├──► Architecture
    ├──► Security
    ├──► Validation
    └──► Metrics
             │
             ▼
      metrics.prom
             │
             ▼
       Flask Service
             │
             ▼
          /metrics
             │
             ▼
         Prometheus
```

The important design principle is that the **discovery/inventory layer establishes the known state of the repository**, while the other analysis engines evaluate different properties of that state.

The Flask service then provides the generated metrics to the observability system.
